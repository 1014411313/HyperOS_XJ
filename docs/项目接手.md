# 项目接手指南

> 给新设备、新模型或新会话中的 AI 助手。先按本指南恢复项目上下文，再处理代码。

## 项目是什么

HyperOS_XJ 是面向多机型、公开分享的公益 Android/HyperOS 模块。它包含单个 Android App、自研 root shell 引擎、LSPosed 背屏功能和模块发行树。用户是非专业使用者：AI 负责规划、调查、实施与验证；只在影响范围、风险或产品选择需要用户决定时，以通俗选项请求批准。

## 接手顺序

1. 阅读仓库根目录 `AGENTS.md`，其规则优先于本指南。
2. 阅读 `docs/开发交接.md` 和 `docs/架构.md`，确认当前代码、分支工作和构建环境。
3. 阅读 `docs/引擎API.md`、`docs/设计规范.md`、`docs/踩坑记录.md`。
4. 阅读 `state/bugs.json` 中仍在 `collecting` 的条目；它是唯一 bug 台账。不要另建重复 bug 清单。
5. 阅读 `docs/项目记忆.md` 的最新记录和 `git status --short`。未提交文件可能是用户或其他代理的工作，先理解，不得擅自回滚。
6. 运行 `python3 scripts/doctor.py`（只读、不联网、不安装）核对双仓库、接手入口与基础环境；构建前用 `--profile build`，发布前用 `--profile release`。再检查当前可用的模型、技能、MCP、SDK、JDK、Gradle 与设备访问工具。配置可能因设备而异，只能报告当下实测状态。
7. 对照用户本轮请求、待办和最新记忆决定下一步；历史授权只覆盖其明确范围。涉及危险或共享状态的操作仍需单独批准。

## 跨设备与跨模型迁移

目标：换电脑、换模型后，新会话只凭仓库内规则与检查脚本就能继续，用户不必口头复述环境。顺序是先恢复规则入口与只读检查，再恢复私密材料，最后才构建或发布。未获授权不迁移凭据、不安装依赖、不 commit/push。

### 工作区与规则入口

- 把本项目目录本身（含 `AGENTS.md` 的那一层）设为工作区根，不要用它的父目录。工作区根决定工具找规则、脚本和 `state/workspace.json` 的位置。
- `AGENTS.md` 是唯一共享规则来源。`CLAUDE.md` 只有 `@AGENTS.md`，`GEMINI.md` 只有 `@./AGENTS.md`，两者只是导入入口，不重复维护规则。
- 只有明确支持该导入语法的工具会自动加载；其他工具不保证读取，接手会话应先显式读 `AGENTS.md` 和本文件。任何模型都不保证 100% 遵守规则，关键约束要靠脚本检查与人工复核，不能只靠提示词。
- 不把整份系统提示词、供应商配置或客户端专有设置复制进仓库；规则以仓库文件为准。

### 两套仓库

在新设备选定同一个父目录后分别克隆（私有仓库通过本机凭据助手认证，不在 URL 中填写令牌）：

```bash
git clone https://gitee.com/xiaomirezhale/HyperOS_XJ.git
git clone https://gitee.com/xiaomirezhale/xj-feedback.git
cd HyperOS_XJ
python3 scripts/doctor.py
```

已有工作目录时先检查本地改动，再决定拉取；不要重复克隆覆盖。

| 仓库 | 位置 | 可见性 | 远端 |
|---|---|---|---|
| HyperOS_XJ（源码与发行） | 本项目根 `.` | 公开 | Gitee `https://gitee.com/xiaomirezhale/HyperOS_XJ.git` 为主远端（origin），GitHub `https://github.com/1014411313/HyperOS_XJ.git` 为镜像 |
| xj-feedback（私有诊断与个人备份） | 相邻 `../xj-feedback`，可用环境变量 `XJ_FEEDBACK_DIR` 覆写 | 私有 | `https://gitee.com/xiaomirezhale/xj-feedback.git` |

- 两个仓库各自独立，放在同一父目录下平级。不要把 xj-feedback 放进 HyperOS_XJ 目录，也不要在任一仓库的工作树内再嵌一个仓库；`.git` 不能互相包含。
- 分别查看状态、分支和远端，分别提交。公开项目的 commit、tag、release 不套用到诊断仓库；诊断仓库的同步、修改、删除和推送需要单独授权。
- 私有仓的 `feedback/` 保存诊断，`memory/` 保存既有个人记忆备份；两者都不能混入公开仓。接手不自动导入或执行备份内容，也不擅自清理；按当前任务授权读取或恢复。
- 诊断包只读分析，不执行包内脚本，不把原始诊断材料或个人信息提交进公开仓库。
- `state/workspace.json` 登记两仓库的相对目录、可见性、origin 和签名信息；`scripts/doctor.py` 会校验每个目录确实是独立仓库根、origin 与登记一致。`XJ_FEEDBACK_DIR` 的相对路径始终相对源码仓库根解析，与启动目录无关。

### 签名（必须私密保存）

- 当前 `assembleDebug` 使用 `~/.android/debug.keystore`（别名 `androiddebugkey`）。这是既有已发布 APK 的签名身份，不是可随手重生成的临时文件。
- 新设备必须把原签名文件私密复制回该路径。不要用 `keytool` 新生成替代：新证书与已发布版本不同，覆盖安装会因签名不一致失败。
- 公钥散列登记在 `state/workspace.json` 的 `android_signing.certificate_sha256`，以文件当前值为准。`doctor.py` 的 build/release 档会用 `keytool` 导出证书、用 `apksigner` 校验现有 APK，再与登记值比对。
- keystore 和私钥不进公开仓库、日志、测试输出或公开迁移包；备份走私密介质或加密存储。证书散列是公开的校验信息，不是签名私钥。

### 工具链版本

| 项 | 固定值 | 说明 |
|---|---|---|
| JDK | 21 或更高 | `doctor.py` 读取 `java -version` 判定 |
| Android SDK 平台 | API 37（目录常见为 `android-37.0`） | 按 `source.properties` 的 `AndroidVersion.ApiLevel` 识别，不按目录名猜 |
| Build Tools | 37.0.0 | 需要 `lib/apksigner.jar` |
| Gradle | Wrapper 固定 `gradle-9.7.1-bin.zip` | 用仓库 Wrapper，不替换系统 Gradle 版本 |
| Python | 3.9 或更高 | 运行 `doctor.py` 和回归脚本 |

- SDK 路径来自 `ANDROID_HOME`/`ANDROID_SDK_ROOT` 或 `ToolboxApp/local.properties` 的 `sdk.dir`。`local.properties` 已被 `.gitignore` 排除，新设备自行生成，不提交。
- Windows 上完整的构建、打包和发布流程在 WSL 的 Bash 中运行；原生 PowerShell 只保留既有的打包脚本 `scripts/package_module.ps1`，不要据此扩展发布流程。

### 首次依赖与 aapt2

- 首次构建需要联网下载依赖：`bash scripts/release_module.sh --local --online`，或手动去掉 `--offline` 运行 Gradle。依赖进入 `GRADLE_USER_HOME` 缓存后，默认走 `--offline`。
- `~/.gradle/gradle.properties` 里可能有 `android.aapt2FromMavenOverride=<绝对路径>`。该路径与本机架构绑定，不能照抄到新机器：路径不存在，或二进制与本机系统和架构不兼容（例如把本机 ARM 的 aapt2 拷到 x86_64 电脑，或反向），都会让构建失败。`doctor.py` 会检查该路径存在且能执行 `version`。
- 不要通过改 Wrapper 版本、换镜像源或删缓存强行绕过环境问题；先按报错核对版本与架构，需要安装时先说明并取得批准。

### Git 身份与远程凭据

- 新设备需要用户本人设置提交身份：`git -C <仓库> config --local user.name` 和 `user.email`。`release_module.sh` 发现缺失时会给出提示，不代填。
- 发布可从 `GITEE_TOKEN`/`GITHUB_TOKEN` 环境变量取令牌，也可从本机标准 Git 凭据助手按主机读取。发布脚本让同一份令牌用于 release API 和 HTTPS 推送，推送认证通过临时 `GIT_ASKPASS` 提供，不把令牌写进远端 URL 或临时脚本。Gitee 登录名默认取源码仓库拥有者，需要时设 `GITEE_USERNAME`。
- `--check` 仅检查对应主机的凭据来源是否配置，不读取或验证权限；正式发布在任何改动前读取两处凭据，缺失即停止。令牌需有对应仓库发布与推送权限。
- 发布和迁移用的账号令牌通过私密配置提供，不写入仓库文件、脚本、测试、日志或公开迁移包，也不在回复中回显。缺凭据时只报告缺失，不要求用户把令牌贴进对话。

### AiCode 客户端备份的边界

- 官方备份包含供应商/AI 配置、Git 凭据、连接方式、MCP、聊天记录和客户端设置；工作区默认不导出，且仓库 `.gitignore` 已排除 `dist/*.zip`、`*.apk`、`references/` 等构建与本地产物。
- 以下内容不保证随官方备份到达新设备，需要逐项私密备份：全局 skills、agents、prompts.custom、tools、memory，以及签名 keystore。仓库内的规则文件、脚本和文档才是可公开复现的部分。
- 禁止把上述私密内容打包进公开仓库或公开迁移包；迁移包仅供本人使用，也不放原始诊断材料。
- 恢复客户端能力时按需逐项恢复：需要哪个技能就恢复哪个并记录清单；整份全局配置可私密加密备份，但不要未经审查复制到公开项目或覆盖另一客户端的内置提示词。MCP 只恢复任务确实需要的服务器，保持最小权限，不为方便放宽权限或全局放行。
- 不把系统提示词全文、供应商密钥或客户端内部配置复制成项目文档；用户换模型后，以 `AGENTS.md` 和本文件作为行为约束的起点。

### 版本状态与交付

- 当前版本状态读根目录 `latest.json`（版本、下载与 release 链接）和 `state/release.json`（版本历史）。`state/latest.json` 是旧快照，不用于判断当前版本。
- 用户说「包」指模块 ZIP：交付发送 ZIP 附件；附件工具不可用时给真实地址并说明，不声称已发送附件。
- 发行链接逐条放在独立的单行代码块中，便于分别复制；除当前版本，还提供 Gitee 和 GitHub 的发行列表页，用户可回退历史版本。
- 迁移和交付过程中只要求凭据不进入日志、测试和公开迁移包；不对令牌存储方式作额外承诺，也不新增令牌专项禁令。上传实现保持现状。

### 迁移检查清单

1. 项目目录设为工作区根，确认 `AGENTS.md` 可读，`CLAUDE.md`/`GEMINI.md` 内容只是导入行。
2. 两仓库平级就位、各自独立，`git status` 已知；需要时再设 `XJ_FEEDBACK_DIR`。
3. `python3 scripts/doctor.py` 的 handoff 档无 FAIL；缺项逐条处理，不跳过。
4. 签名文件已私密恢复，散列与 `state/workspace.json` 一致（`--profile build`）。
5. 需要发布时再跑 `--profile release` 或 `scripts/release_module.sh --check`，确认凭据只报告存在与否。
6. 构建与发布前确认 JDK、SDK、Build Tools、Gradle 版本符合上表，Windows 在 WSL 中执行。
7. 交付按 ZIP 附件与单行代码块链接执行。

## 用户协作方式

- 用户可只描述目标、故障现象或希望的结果。AI 应自主读取诊断、定位代码、规划变更、实现和测试，不让用户自行查路径、读源码或执行开发命令。
- 开始多步骤任务时建立待办并持续更新。每个阶段用简短中文说明正在做什么、已得到什么结论。
- 用户批准前可以做只读调查和可逆的本地验证；未经批准不刷机、不写设备分区、不安装模块、不推送远程、不发布、不装系统级依赖，也不扩大修复范围。
- 如果必须真机验证，先说明为什么本地模拟不能替代，再提供尽量短且分步骤的操作指引。用户可把诊断包交给 AI 分析；AI 不要求用户自行解读日志。
- 汇报时区分：已从源码确认、诊断直接观察、模拟通过、真机验证、尚未证实。不得把相关性说成因果，不得声称未运行的构建或测试通过。

## 多机型与公益发行

- 所有机型特性均做运行时检测，覆盖 SoC/平台、系统版本、节点、节点单位、权限、启动槽位、PID1 命名空间及目标包等实际相关能力。
- 不根据型号名猜路径或单位；支持表只能是有证据、有限定的映射。配置文本不是可信硬件身份来源。
- 探测结果为空、权限拒绝、多个候选冲突或读回不符时，拒绝该项写入并保留系统原状。分区写入、DTBO、挂载和温控类操作默认 fail-closed，具备可验证备份、确认和恢复路径。
- 模拟测试覆盖至少：已支持、明确不支持、未知、权限拒绝、节点缺失、单位/节点类型不符、候选冲突、回读失败及恢复失败。覆盖不到的机型应明确标注未验证。
- 不在公开迁移包、日志或测试输出中包含迁移用的账号凭据、个人诊断包或用户隐私。只对公开、无凭据资源使用外部镜像；私有仓库鉴权信息不发给第三方。既有诊断上传实现保持不变。
- 单机真机通过不代表多机型兼容；模拟通过也不代表真机通过。对外只发布验证覆盖范围，不宣传无证据的兼容性。

## 技能与工具

技能/MCP/运行时因设备、会话及模型设置而变化。本表记录的是选择规则，不宣称所有接手设备都已安装。

| 工作 | 优先使用 |
|---|---|
| 诊断包、异常或测试失败 | `debugging-and-error-recovery`；只读解析，不执行归档中的命令 |
| 实施前的多步骤任务 | `writing-plans`；同时使用项目待办记录进度 |
| 编写代码、最小改动 | `ponytail`，遵守仓库现有风格 |
| 改动完成前检查 | `verification-before-completion`；按风险补 `code-review-and-quality` 或 `ponytail-review` |
| 前端 UI 设计 | `frontend-design`；网页功能测试用 `webapp-testing` |
| 性能问题 | `performance-optimization` |
| Android shell 回归 | Python 3 隔离沙箱、`sh -n`/`bash -n`、`git diff --check`、engine/dist 一致性比较 |
| Android App 构建 | 仓库 Gradle Wrapper 与当前可用 JDK/SDK；构建前检查本地已有终端/缓存，不假设环境状态 |
| 环境、双仓库与迁移自检 | `python3 scripts/doctor.py`（`--profile build`/`release`）；只读，不联网、不安装、不打印凭据 |
| 真机系统辅助 | 当前会话实际提供的 ADB/Shizuku/设备工具；每次涉及设备写入必须取得明确批准 |
| 文档/MCP/媒体文件 | 按任务加载 `docx`、`pdf`、`pptx`、`xlsx`、`mcp-builder` 等相应技能；不用无关工具 |

不因技能表而强制加载所有技能。安装技能、MCP、依赖或系统工具前先说明来源、权限、存放位置与必要性，并取得批准。工具不可用时如实说明，采用现有安全替代验证或标注未验证，不谎报。

## 项目记录

- `state/bugs.json`：唯一 bug 状态台账。反馈、根因、修复计划及验证状态放这里。
- `docs/项目记忆.md`：按日期追加重要修复、架构决定、验证证据、失败与根因、环境变化、兼容性限制和已知待办。记录准确短小，避免复制完整日志、凭据或个人诊断内容。
- 版本状态：根目录 `latest.json` 记录当前发行与下载链接，`state/release.json` 记录版本历史；`state/latest.json` 是旧快照，不用于判断当前版本。
- 迁移与恢复：见本文件「跨设备与跨模型迁移」；私密材料逐项备份，不写入公开仓库或迁移包。
- `docs/踩坑记录.md`：已证实且可复用的技术教训及其正确做法；未证实假设不要写成事实。与 bug 状态重复时链接 bug ID，不维护第二份台账。
- 本文件：长期有效的协作方式、多机型安全边界、接手次序和工具/技能选择规则；模型切换后仍应有效。
- 会话待办：追踪当前可执行任务和等待用户决策的事项。交付后只保留真实未完成/待确认项。
- 不创建每轮重复的报告或无主文档。需要持续跟踪的修复回写既有台账与项目记忆。

## 每次修改后的记录

对会影响运行行为的修改，在 `docs/项目记忆.md` 追加一条，至少写清：

- 日期、涉及的 bug ID/用户目标和文件；
- 改了什么及目的；
- 根因依据与关键边界；
- 运行过的测试/构建及其结果；
- 未覆盖的机型、系统或真机行为；
- 用户批准范围、危险操作是否执行（例如仅模拟，未安装/未刷写）。

纯拼写或格式变更可不单独记录；不要写“全部修好”这类超出证据的话。

## 结构与安全底线

- `engine/` 是引擎唯一编辑源，改后同步 `dist/HyperOS_XJ_New/engine/`。
- 单 App `com.hyperos.xj`；Xposed stub 仅 `compileOnly`。
- 不禁用原生背屏时钟，不默认推送任务到其他显示器。
- DTBO、分区、安装、打包、发布及远程写操作严格按 `AGENTS.md` 审批门；仅本地模拟获批不等于真机写入获批。
- 不覆盖、清理或回滚未确认归属的工作树改动；不擅自 commit、push、reset 或删除用户产物。
