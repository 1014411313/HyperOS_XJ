# 项目接手指南

> 给新设备、新模型或新会话中的 AI 助手。先按本指南恢复项目上下文，再处理代码。

## 项目是什么

HyperOS_XJ 是面向多机型、公开分享的公益 Android/HyperOS 模块。它包含单个 Android App、自研 root shell 引擎、LSPosed 背屏功能和模块发行树。用户是非专业使用者：AI 负责规划、调查、实施与验证；只在影响范围、风险或产品选择需要用户决定时，以通俗选项请求批准。

## 接手顺序

1. 阅读仓库根目录 `AGENTS.md`，其规则优先于本指南。
2. 阅读 `docs/开发交接.md` 和 `docs/架构.md`，确认当前代码、分支工作和构建环境。
3. 阅读 `docs/引擎API.md`、`docs/设计规范.md`、`docs/踩坑记录.md`。
4. 阅读 `state/bugs.json` 中仍在 `collecting` 的条目；它是唯一 bug 台账。不要另建重复 bug 清单。
5. 阅读 `docs/项目记忆.md` 的最新记录和 `git status --short`。未提交文件可能是用户或其他代理的工作，先理解，不得擅自回滚。
6. 检查当前可用的模型、技能、MCP、SDK、JDK、Gradle 与设备访问工具。配置可能因设备而异，只能报告当下实测状态。
7. 对照用户本轮请求、待办和最新记忆决定下一步；历史授权只覆盖其明确范围。涉及危险或共享状态的操作仍需单独批准。

## 用户协作方式

- 用户可只描述目标、故障现象或希望的结果。AI 应自主读取诊断、定位代码、规划变更、实现和测试，不让用户自行查路径、读源码或执行开发命令。
- 开始多步骤任务时建立待办并持续更新。每个阶段用简短中文说明正在做什么、已得到什么结论。
- 用户批准前可以做只读调查和可逆的本地验证；未经批准不刷机、不写设备分区、不安装模块、不推送远程、不发布、不装系统级依赖，也不扩大修复范围。
- 如果必须真机验证，先说明为什么本地模拟不能替代，再提供尽量短且分步骤的操作指引。用户可把诊断包交给 AI 分析；AI 不要求用户自行解读日志。
- 汇报时区分：已从源码确认、诊断直接观察、模拟通过、真机验证、尚未证实。不得把相关性说成因果，不得声称未运行的构建或测试通过。

## 多机型与公益发行

- 所有机型特性均做运行时检测，覆盖 SoC/平台、系统版本、节点、节点单位、权限、启动槽位、PID1 命名空间及目标包等实际相关能力。
- 不根据型号名猜路径或单位；支持表只能是有证据、有限定的映射。配置文本不是可信硬件身份来源。
- 探测结果为空、权限拒绝、多个候选冲突或读回不符时，拒绝该项写入并保留系统原状。分区写入、DTBO、挂载和温控类操作默认 fail-closed，具备可验证备份、确认和恢复路径。
- 模拟测试覆盖至少：已支持、明确不支持、未知、权限拒绝、节点缺失、单位/节点类型不符、候选冲突、回读失败及恢复失败。覆盖不到的机型应明确标注未验证。
- 不在公开包、日志或测试输出中包含令牌、个人诊断包、私人路径数据或用户隐私。只对公开、无凭据资源使用外部镜像；私有仓库凭据不得传给代理或第三方。
- 单机真机通过不代表多机型兼容；模拟通过也不代表真机通过。对外只发布验证覆盖范围，不宣传无证据的兼容性。

## 技能与工具

技能/MCP/运行时因设备、会话及模型设置而变化。本表记录的是选择规则，不宣称所有接手设备都已安装。

| 工作 | 优先使用 |
|---|---|
| 诊断包、异常或测试失败 | `debugging-and-error-recovery`；只读解析，不执行归档中的命令 |
| 实施前的多步骤任务 | `writing-plans`；同时使用项目待办记录进度 |
| 编写代码、最小改动 | `ponytail`，遵守仓库现有风格 |
| 改动完成前检查 | `verification-before-completion`；按风险补 `code-review-and-quality` 或 `ponytail-review` |
| 前端 UI 设计 | `frontend-design`；网页功能测试用 `webapp-testing` |
| 性能问题 | `performance-optimization` |
| Android shell 回归 | Python 3 隔离沙箱、`sh -n`/`bash -n`、`git diff --check`、engine/dist 一致性比较 |
| Android App 构建 | 仓库 Gradle Wrapper 与当前可用 JDK/SDK；构建前检查本地已有终端/缓存，不假设环境状态 |
| 真机系统辅助 | 当前会话实际提供的 ADB/Shizuku/设备工具；每次涉及设备写入必须取得明确批准 |
| 文档/MCP/媒体文件 | 按任务加载 `docx`、`pdf`、`pptx`、`xlsx`、`mcp-builder` 等相应技能；不用无关工具 |

不因技能表而强制加载所有技能。安装技能、MCP、依赖或系统工具前先说明来源、权限、存放位置与必要性，并取得批准。工具不可用时如实说明，采用现有安全替代验证或标注未验证，不谎报。

## 项目记录

- `state/bugs.json`：唯一 bug 状态台账。反馈、根因、修复计划及验证状态放这里。
- `docs/项目记忆.md`：按日期追加重要修复、架构决定、验证证据、失败与根因、环境变化、兼容性限制和已知待办。记录准确短小，避免复制完整日志、凭据或个人诊断内容。
- `docs/踩坑记录.md`：已证实且可复用的技术教训及其正确做法；未证实假设不要写成事实。与 bug 状态重复时链接 bug ID，不维护第二份台账。
- 本文件：长期有效的协作方式、多机型安全边界、接手次序和工具/技能选择规则；模型切换后仍应有效。
- 会话待办：追踪当前可执行任务和等待用户决策的事项。交付后只保留真实未完成/待确认项。
- 不创建每轮重复的报告或无主文档。需要持续跟踪的修复回写既有台账与项目记忆。

## 每次修改后的记录

对会影响运行行为的修改，在 `docs/项目记忆.md` 追加一条，至少写清：

- 日期、涉及的 bug ID/用户目标和文件；
- 改了什么及目的；
- 根因依据与关键边界；
- 运行过的测试/构建及其结果；
- 未覆盖的机型、系统或真机行为；
- 用户批准范围、危险操作是否执行（例如仅模拟，未安装/未刷写）。

纯拼写或格式变更可不单独记录；不要写“全部修好”这类超出证据的话。

## 结构与安全底线

- `engine/` 是引擎唯一编辑源，改后同步 `dist/HyperOS_XJ_New/engine/`。
- 单 App `com.hyperos.xj`；Xposed stub 仅 `compileOnly`。
- 不禁用原生背屏时钟，不默认推送任务到其他显示器。
- DTBO、分区、安装、打包、发布及远程写操作严格按 `AGENTS.md` 审批门；仅本地模拟获批不等于真机写入获批。
- 不覆盖、清理或回滚未确认归属的工作树改动；不擅自 commit、push、reset 或删除用户产物。
