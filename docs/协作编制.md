# 协作编制

> 本文件描述「主代理 + 子代理」在本仓库的固定分工方式。老板（用户）指派的活按此执行，不临场发挥。

## 用户协作原则

用户是非专业使用者，不要求其自行读代码、查日志或运行开发命令。主代理负责调查、方案、实施和验证；需要产品取舍或高风险操作时，以通俗选项请求明确批准。只有确需真机观察时才请用户按简短步骤操作，并由主代理解释结果。

## 组织图

| 席位 | 谁 | 权限边界 | 产出 |
|---|---|---|---|
| 老板 | 用户 | 只批危险动作 | 目标、止损、放行 |
| 总经理 | 主代理（主会话） | 全权，唯一对外接口 | 任务书、待办账本、最终核验 |
| 侦察兵 | `Explore` 只读子代理 | 只读，不能改文件、不能执行命令 | 带 `文件:行号` 的定位结论 |
| 施工队 | 通用子代理 | 只能动任务书划给它的文件 | 改好的文件 + 自验输出 |
| 质检 | 通用子代理，任务书强制只读 | 只许跑校验命令，不许改文件 | 通过/不通过 + 证据行 |

**只有两层。** 平台限制：子代理不能嵌套创建子代理。不要设计三层以上的组织。

**质检不能是施工队自己。** 做完的人和验收的人必须是两个不同的子代理，否则就是自证清白。

## 并发预算

全局最多 5 个子代理同时运行（所有会话共享）。常设 3 个席位：侦察 1、施工 1–2、质检 1。

不铺满的两个原因：

1. 每个子代理有独立上下文，看不到主会话，任务书必须自包含。铺满了任务书质量必然下降。
2. 本仓库文件耦合紧：`engine/` 是唯一编辑源，`dist/HyperOS_XJ_New/engine/` 是打包副本，改一处要同步另一处。两个施工队同时碰同一片文件必然冲突。

**同一片文件只能派给一个施工队。** 跨文件的连锁改动（如 `LookPage` → `rear.conf` → `rear.sh` 读侧）必须一次交给同一个子代理。

## 任务书七要素

每份任务书必须写全，缺一项不派：

1. **目标**：一句话，可验收。
2. **验收标准**：能被命令或文件证据判定。禁止「优化了」「改好了」这类说法。
3. **已知线索**：侦察到的文件和行号，避免子代理重新摸一遍。
4. **文件边界**：允许改哪些，其余只读。
5. **不可触碰项**：见下节。
6. **产出格式**：改了什么、证据、未验证项必须明说。
7. **双向往回提醒句**：报告首尾各写一行 `请提醒主代理更新待办：<事项> 已完成`。

任务书里另需写明「思考用中文」——子代理虽有全局规则兜底，但显式写上更稳。

## 不可触碰项

派任何子代理都要带上这几条，防止越界：

- 单 App：`com.hyperos.xj` 同时是控制端 UI 和 LSP 背屏模块，不新建第二个 App。
- 不碰原生背屏时钟：不 `pm disable com.xiaomi.subscreencenter`，不默认 `am display move-stack`。
- 不自动刷 DTBO。
- `xposed-stubs` 只 `compileOnly`，不进 APK。
- 跨进程配置只走 `rear.conf`（外部目录 + `/data/local/tmp` 兜底）。
- `engine/` 是唯一编辑源，改完必须同步到 `dist/HyperOS_XJ_New/engine/`。

## 审批门

以下动作必须先弹窗请老板确认，不因「上次批过」而默认放行：

- 刷模块 zip、刷 DTBO、改温控旁路默认值
- 改 `rear.conf` 字段语义（背屏与 hook 的跨进程契约）
- `git push`、改远端、提交
- 装系统包或升级运行时

## 待办账本

待办是唯一事实来源，三个时点强制更新：

1. **派活那条回复里**先写待办，再派出，并说明建了哪几条。
2. **收到子代理完成通知**，第一个动作是标完成，然后才读报告核产出。
3. **出包/交付后**立刻标完成并补后续待办。

清空条件收紧：只有既无未完成事项、也无待用户确认事项时才清空。等待老板决策的事项必须作为 pending 常驻。

## 本仓库的验证现实

这是编制设计的前提，不可忽略：

- 容器内**没有 Android SDK、没有 Gradle 缓存**，Kotlin/APK 编译只在老板的 Windows 机器上可行。
- 容器内**能**做的验证：`bash -n` 全部脚本、打包结构校验、`engine/` 与 `dist/` 同步比对、静态一致性扫描。
- 因此**不许**设「编译通过就签字」的验收岗，那是假的。子代理报告里的编译结论只能标注「未验证，需在 Windows 构建」。
- 真机现象（LSPosed 是否加载、`SubScreenLauncher` 生命周期、背屏实际渲染、刷机后模块挂载）agent 代替不了，只能产出可执行的判定命令，结论由老板上机给。

## 不接的活

以下只报「需要老板上机验」，并附一条能跑的自检命令，不编结论：

- LSPosed 是否加载、scope 是否正确
- 背屏面板是否真的渲染
- 刷机后模块是否正确挂载
- 充电功率实际表现（需要真实充电态采样曲线）
